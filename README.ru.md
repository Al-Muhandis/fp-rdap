# fp-rdap

[English](README.md) | Русский

RDAP-клиент для Free Pascal / Lazarus: запросы к реестрам доменов и IP-адресов по протоколу
RDAP ([RFC 9082]/[RFC 9083]) с роутингом через официальные IANA bootstrap-файлы
([RFC 8524], [RFC 9224], [RFC 9225]).

## Возможности

- Запросы: `domain`, `ip`, `autnum`, `entity`.
- IDNA: U-label домены (например, `пример.рф`) конвертируются в A-label
  до запроса и поиска в bootstrap — punycode (RFC 3492) плюс прагматичное
  IDNA-маппирование fp-idn (приведение регистра, разделители label,
  отклонение недопустимых имён).
- Автоматический выбор RDAP-сервера по домену (multi-label TLD, `co.uk`) или IP
  (longest-prefix-wins) из bootstrap-файлов IANA; bootstrap-файлы грузятся с диска или из строки.
- Статусы результата: `rqsOK`, `rqsNotFound`, `rqsRateLimited`, `rqsError` + разбор
  RDAP error-объекта (`errorCode`/`title`) и заголовка `Retry-After`.
- Таймауты соединения/IO, User-Agent, редиректы, лимит размера ответа
  (`MaxResponseSize`, по умолчанию 10 МБ, 0 — без ограничения).
- SOCKS5-прокси: `ProxyHost`/`ProxyPort`/`ProxyUser`/`ProxyPass` — при непустом
  `ProxyHost` запросы идут через прокси (транспорт переключается на Synapse
  `THTTPSend`, TLS — через OpenSSL-плагин Synapse); при пустом — прежнее
  поведение 1-в-1 (паритет с fp-whois `TWhoisClient`).
- Встроенный мок (`TRDAPClientMock`) для тестов без сети.

## Структура

| Путь | Назначение |
|------|------------|
| `src/rdapclient.pas` | Вся библиотека: клиент, bootstrap, чистые хелперы (IP/CIDR/домены) |
| `rdap_rt.lpk` | Lazarus-пакет (runtime-only) |
| `tests/` | FPCUnit-тесты: консольный и GUI-раннер |
| `demo/` | Консольное демо |

## Установка

Установите пакет `rdap_rt.lpk` в Lazarus (Package → Open → Install) или просто добавьте
`src/rdapclient.pas` в проект. Требуется FPC 3.2+, FCL (fpjson, fphttpclient), пакет
[`fpidn_rt`](https://github.com/al-muhandis/fp-idn) (fp-idn, punycode для IDNA-конвертации),
пакет Synapse (`laz_synapse` — транспорт SOCKS5-прокси)
и OpenSSL библиотеки в PATH для HTTPS.

## Быстрый старт

```pascal
uses rdapclient;

var
  B: TRDAPBootstrap;
  C: TRDAPClient;
begin
  // Файлы с https://data.iana.org/rdap/ положите рядом с программой
  B := TRDAPBootstrap.Create;
  try
    B.LoadFromLocalFiles('dns.json', 'ipv4.json', 'ipv6.json');
    // Либо из строки: B.LoadDNSFromString(EmbeddedDNSSnapshot);

    C := TRDAPClient.Create;
    try
      C.Bootstrap := B;                       // bootstrap не принадлежит клиенту
      C.QueryDomain('example.com');
      case C.LastStatus of
        rqsOK:          Writeln(C.GetObjectTitle, ' | ', C.GetObjectType);
        rqsNotFound:    Writeln('Not found');
        rqsRateLimited: Writeln('Rate limited, retry after ', C.RetryAfter, 's');
      end;
    finally
      C.Free;
    end;
  finally
    B.Free;
  end;
end;
```

Без bootstrap задайте `C.BaseURL := 'https://rdap.org/'` — но тогда `QueryAutNum`/`QueryEntity`
также потребуют явного `BaseURL` (bootstrap их не покрывает).

Для тестов своего кода используйте `TRDAPClientMock`: `SetupMock(json, code)`,
`SetupMock(json, code, ['Retry-After: 120'])` (с заголовками ответа),
`SetupMockError(msg)`, история URL — `MockRequestURL(i)`.

## Демо

`demo/rdap_demo.lpi` — положите рядом с exe файлы `dns.json`, `ipv4.json`, `ipv6.json`
с https://data.iana.org/rdap/ ; без них демо уходит через `https://rdap.org/`.

На Windows демо переключает вывод консоли в UTF-8 (`SetConsoleOutputCP`) на время
работы и возвращает прежний кодипейдж при выходе — не-ASCII строки (названия
объектов, error-сообщения, JSON-превью) печатаются без mojibake; нужен шрифт
консоли с поддержкой Unicode (в современных Windows он по умолчанию).

Ручная проверка SOCKS5-транспорта с живым прокси:

```bash
rdap_demo --proxy=127.0.0.1:1080 --proxy-user=u --proxy-pass=p
```

Без `--proxy` демо ходит напрямую, как и раньше.

## Ограничения

- Клиент не потокобезопасен: один экземпляр на поток.
- IDNA — punycode (RFC 3492) плюс прагматичное IDNA-маппирование fp-idn:
  приведение регистра (ASCII, кириллица `U+0400..U+042F`, греческий),
  разделители `．`/`。`/`｡` трактуются как `.`, недопустимые label
  (управляющие символы и пробел, `<>"/\?#@:|`, лимиты длины DNS 63/253)
  отклоняются с `ERDAPError`. Без NFC-нормализации: составная и разложенная
  формы одного имени кодируются в разные A-label — передавайте имена в NFC.
- Ответ больше `MaxResponseSize` (по умолчанию 10 МБ) обрывается с `ERDAPError`;
  0 отключает лимит.
- SOCKS5-прокси-режим (при непустом `ProxyHost`) отличается от прямой дороги:
  - только SOCKS5 (`SocksType` — дефолт Synapse); SOCKS4 не поддерживается;
    no-auth при пустом `ProxyUser`, user/pass при заданном;
  - `MaxResponseSize` применяется **после** полной загрузки тела: обрыва
    скачивания mid-read, как на прямой дороге, нет — тело сверх лимита
    скачивается целиком и только потом отвергается;
  - редиректы обрабатываются вручную: до 5 переходов, только абсолютные
    `Location` (http/https); относительный `Location` даёт `ERDAPError`;
  - TLS поверх туннеля SOCKS5 прозрачен, но для HTTPS-целей нужны
    OpenSSL-библиотеки — как и на прямой дороге;
  - сетевой TLS-over-SOCKS юнит-тестами не покрывается (loopback-стаб не
    говорит TLS; туннель прозрачен, доверяем плагину Synapse).

## Изменения

Журнал релизов — в [CHANGELOG.ru.md](CHANGELOG.ru.md).

### 2026-11-15 — SOCKS5-прокси в транспорте (этап 6 дорожной карты)

- Новое: свойства `ProxyHost`/`ProxyPort`/`ProxyUser`/`ProxyPass` (паритет с
  fp-whois `TWhoisClient`; `ProxyPort` без скрытого дефолта). При непустом
  `ProxyHost` запросы идут через SOCKS5-прокси; при пустом — поведение не
  изменилось ни в чём (все прежние тесты зелёные без правок).
- Транспорт прокси-режима — Synapse `THTTPSend`; новая зависимость
  `rdap_rt.lpk` — `laz_synapse`. no-auth при пустом `ProxyUser`, user/pass
  при заданном (проверено по исходникам Synapse 40.1: `SocksOpen` выбирает
  SOCKS5 всегда при дефолтном `SocksType`, опасение дорожной карты о SOCKS4
  на эту версию не распространяется). `ConnectTimeout`/`IOTimeout`
  применяются и здесь; TLS поверх туннеля — через `ssl_openssl`-плагин.
- Редиректы в прокси-режиме — ручной цикл до 5 переходов (паритет
  `AllowRedirect`/`MaxRedirects=5` прямой дороги), только абсолютные
  `Location`; относительный — `ERDAPError`.
- `MaxResponseSize` в прокси-режиме применяется после полной загрузки тела
  (обрыв mid-read, как на прямой дороге, невозможен) — расхождение
  задокументировано в «Ограничениях».
- `Retry-After`, заголовки ответа и error-объекты работают на обеих дорогах
  одинаково (снапшот заголовков нормализуется к разделителю `:` — у Synapse
  он был `=`, что ломало бы поиск заголовков).
- Тесты: loopback SOCKS5-стаб (`TThread` + слушающий сокет, без сети и DNS):
  8 новых тестов — 200/429+`Retry-After`/отказ CONNECT/302-редирект/
  относительный `Location`/user-pass/дефолты свойств; всего 80 тестов.
- Демо: CLI-параметры `--proxy=host:port`, `--proxy-user=`, `--proxy-pass=`
  для ручной проверки с живым прокси.
- Сборка: команды AGENTS.md/README переключены на инсталляцию
  `C:\laz-4.8` (`--pcp=C:\laz-4.8\config_lazarus`) — прежний `C:\lazarus`
  неработоспособен, а его конфиг ссылался на несуществующий путь `laz_synapse`.
- Релизные шаги (версия lpk, `FpRdap.json` DependenciesAsString, запись
  CHANGELOG, тег/CI) — при публикации, как договорились в дорожной карте.

### 2026-11-14 — Адаптация к fp-idn 1.1.0.0: IDNA-валидация и приведение регистра

- **Изменение поведения:** `DomainToASCII` поднимает `ERDAPError` («Domain
  rejected by IDNA validation…») для доменов, отклонённых валидацией fp-idn
  (пробел/управляющие символы в label, `<>"/\?#@:|`, лимиты длины DNS).
  Раньше (fp-idn до 1.1.0.0) невалидный домен молча давал пустой результат
  и уходил в запрос с пустым путём.
- Приведение регистра (MVP: ASCII, кириллица, греческий): `Example.COM` →
  `example.com`, `ПРИМЕР.РФ` теперь кодируется в зарегистрированный A-label
  `xn--e1afmkfd.xn--p1ai` (раньше имя проходило байт-в-байт и давало
  посторонний A-label). Разделители `．`/`。`/`｡` трактуются как `.`.
- Пакет `rdap_rt` объявляет минимальную версию зависимости `fpidn_rt` 1.1.
- Без NFC-нормализации — как и раньше: имена передавайте в NFC.
- Тесты: свёртывание регистра, отклонение невалидного домена хелпером и
  клиентом (запрос не уходит в сеть); «Ограничения» переписаны.

### 2026-11-14 — IDNA: U-label конвертируются в A-label (бэклог)

- **Изменение поведения:** `QueryDomain` больше не отклоняет не-ASCII домены
  (U-label): каждый не-ASCII label конвертируется в punycode A-label
  (`пример.рф` → `xn--e1afmkfd.xn--p1ai`, RFC 3492 через пакет fp-idn) до
  поиска bootstrap-сервера и отправки запроса. Раньше такой домен отклонялся
  с `ERDAPError` («Domain must be an ASCII A-label…»).
- Конвертация выполняется до выбора сервера: официальные bootstrap-файлы
  RFC 9224 перечисляют IDN-TLD ключи в A-label форме (`dns.json` — чисто
  ASCII), поэтому U-label домены теперь корректно маршрутизируются.
- Новый чистый хелпер `DomainToASCII` (экспортирован для тестов): ASCII-имена,
  включая уже готовые A-label, проходят байт-в-байт; конвертация — только
  punycode, без nameprep/UTS-46 нормализации и приведения регистра
  (подробности — в «Ограничениях»).
- Новая зависимость: runtime-пакет `fpidn_rt` ([fp-idn](https://github.com/al-muhandis/fp-idn)),
  требуется для `rdap_rt.lpk`.
- README: в «Ограничениях» исправлен устаревший пункт про неограниченный
  размер ответа (противоречил `MaxResponseSize` из предыдущей записи бэклога).

### 2026-11-14 — Ограничение размера HTTP-ответа (бэклог)

- **Изменение поведения:** новое свойство `TRDAPClient.MaxResponseSize` —
  максимальный размер тела ответа в байтах, по умолчанию 10 МБ; 0 (или меньше)
  отключает ограничение. Ответ больше лимита не читается в память целиком:
  реальный клиент обрывает скачивание на первом же «переборе» с `ERDAPError`
  («Response from … exceeds the size limit…»). Раньше тело любого размера
  читалось полностью — кривой/враждебный сервер мог исчерпать память.
- При превышении: статус `rqsError`, тело в `LastRawJSON` не сохраняется,
  `LastHTTPCode` содержит фактический код HTTP-ответа (если он дошёл).
  Лимит инклюзивен: тело ровно в `MaxResponseSize` байт проходит. Ограничение
  применяется и к моку (тот же контракт в `ExecuteQuery`), поэтому проверяется
  юнит-тестами без сети.

### 2026-11-13 — Чистота и мелочи (этап 5 дорожной карты)

- **Изменение поведения:** `QueryDomain` отклоняет не-ASCII домены (U-label,
  например `пример.рф`) с `ERDAPError` («Domain must be an ASCII A-label…»).
  RFC 9082 ждёт A-label/punycode в пути URL; раньше U-label отправлялся как
  percent-encoded UTF-8, на что RDAP-серверы не отвечают корректным результатом.
  IDNA-конвертация по-прежнему не поддерживается.
- Нормализация хвостового `/` у base URL выполняется в одной точке — при
  построении URL запроса. `Create` и свойство `BaseURL` хранят значение как
  задано (раньше `Create` добавлял `/` на месте). Итоговые URL запросов
  не изменились.
- Демо: имя сохраняемого файла `rdap_example_*.json` санитизируется — символы,
  недопустимые в именах файлов Windows (`:`, `/` и др.), заменяются на `_`.
- Хинты компилятора в исходниках библиотеки устранены: `FillChar` в
  `TryStrToIPv6` заменён на явную инициализацию нулевыми константами.

### 2026-11-13 — Надёжность bootstrap (этап 4 дорожной карты)

- Все методы загрузки bootstrap (`LoadDNS`/`LoadIPv4`/`LoadIPv6`/`Load*FromString`)
  работают по схеме «разбор → подмена»: неудачная перезагрузка (битый или
  отсутствующий файл, JSON без `services`) больше не оставляет bootstrap пустым —
  ранее загруженные данные продолжают работать. Раньше поля очищались до разбора.
- Выбор base URL из записи bootstrap валидируется строго: URL-часть записи обязана
  быть массивом строк (допустима и одна строка), все элементы — строки, URL не пуст.
  Нарушение → `ERDAPError` с номером записи («Service N»); «чужие» исключения
  fpjson (`EConvertError`/`EJSONError`) наружу больше не выходят.
- Новые методы `LoadIPv4FromString`/`LoadIPv6FromString` — симметрично
  `LoadDNSFromString`.

### 2026-11-13 — Коды ошибок RFC 9083 (этап 3 дорожной карты)

- **Ломающее изменение:** HTTP 400/401/403/503 больше не бросают исключение —
  как 404/429, они приходят как статус `rqsError`. Тело ответа (RFC 9083 §6.2
  error-объект) разбирается в `LastErrorCode`/`LastErrorTitle`/`LastJSON`,
  сырой текст остаётся в `LastRawJSON`; если тело не JSON, статус всё равно
  `rqsError`, а `LastErrorCode` = 0. Раньше эти коды приводили к `ERDAPError`
  («Unexpected response status code»).
- Ответы с кодами вне списка `[200, 400, 401, 403, 404, 429, 503]` (например,
  500) по-прежнему приводят к исключению `ERDAPError`.

### 2026-11-13 — Заголовки ответа и Retry-After (этап 2 дорожной карты)

- Заголовки последнего ответа — часть общего механизма клиента: снапшот хранится
  в защищённом поле `TRDAPClient` (очищается перед каждым запросом), доступ через
  protected virtual `GetResponseHeader`. Разбор `Retry-After` перенесён из
  `DoHTTPGetJSON` в `ProcessLastResponse` — единый путь для реального клиента и мока.
- `RetryAfter` теперь понимает обе формы RFC 7231: число секунд и HTTP-date
  (дата в прошлом → 0, нечитаемое значение → 0). Раньше распознавалась только
  форма «число секунд». Новый чистый хелпер — `TryParseRetryAfter`.
- Мок может задавать заголовки ответа: `SetupMock(json, code, ['Retry-After: 120'])`.
- Наблюдаемое поведение почти не изменилось: `RetryAfter` теперь ненулевой для
  date-формы заголовка и обнуляется, если ответ не дошёл до разбора
  (например, 200 с битым JSON).

### 2026-11-13 — UTF-8 корректность (этап 1 дорожной карты)

- Все строки библиотеки — UTF-8 по контракту. Модуль `rdapclient` в секции
  `initialization` выставляет `DefaultSystemCodePage := CP_UTF8` на весь процесс:
  без этого fcl-json из FPC 3.2.2 на Windows с не-UTF-8 системной кодировкой
  портит `\uXXXX`-эскейпы и литеральные не-ASCII байты при разборе ответов
  при любом значении флага `GetJSON`. Подключение модуля переопределяет
  кодипейдж по умолчанию у хост-приложения — учитывайте это, если приложение
  полагается на системную ANSI-кодировку.
- Bootstrap-файлы читаются явно как UTF-8 (`LoadFromFile(..., TEncoding.UTF8)`):
  раньше `TStrings` декодировал их системной ANSI-кодировкой.
- `ParseJSONSafe`/`TryParseJSON` используют `GetJSON(..., True)`.

### 2026-11-14 — парс-граница не зависит от кодипейджа (бэклог: fcl-json и UTF-8)

- Уточнение к записи от 2026-11-13: на Windows с не-UTF-8 системной кодировкой
  fcl-json 3.2.2 портит литеральные не-ASCII байты при любом значении флага
  `GetJSON` (конверсия кодипейджа на границе вызова `string` → `UTF8String`),
  а `\uXXXX`-эскейпы — только при `UseUTF8=False` (проверено пробником на
  cp1251; при `UseUTF8=True` эскейпы выживают).
- `ParseJSONSafe`/`TryParseJSON` передают в `GetJSON` приватную копию тела,
  перемеченную в `CP_UTF8` без конверсии (`Utf8JSONArg`): разбор не зависит от
  метки кодипейджа входной строки. На хосте с UTF-8-кодипейджем это no-op,
  наблюдаемое поведение не изменилось.
- Глобальная установка `DefaultSystemCodePage := CP_UTF8` остаётся необходимой:
  чтение разобранных значений (`AsString` → `String`) и загрузка
  bootstrap-файлов конвертируют кодипейдж. По исходникам FPC 3.3.1 fcl-json
  разбирает вход кодипейдж-независимо (сканер сам кодирует эскейпы в UTF-8 и
  метит токены `CP_UTF8`), но выходные конверсии — нет: снятие глобальной
  установки возможно только после рефакторинга всех строковых границ
  (план — в дорожной карте).
